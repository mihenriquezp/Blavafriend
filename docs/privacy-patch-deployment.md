# Privacy patch: rollout and recovery

This patch addresses three boundaries: birth-year delivery through the API, informed choice about shared Cohort familiarity statistics, and incomplete account deletion. It does **not** change cohort email eligibility, the profile-claiming model, or cross-account browser tool storage. No production migration or real account deletion is performed by the tests.

## Behavior

- `students.birth_year` remains for old clients but is constrained to NULL. Existing years are moved to `student_private`, whose RLS allows only the account linked to that profile to read/write its year. App admins have no exception. Ownership still means the current profile linkage; the deferred claiming/identity issue remains relevant. Other publicly entered fields such as age, birthday day and month are unchanged.
- `update_student_profile` saves the shared fields and private year in one transaction, rejects unexpected fields and enforces ordinary RLS. Admins can still edit shared profile fields. Cached clients can still save their own non-null year: a database trigger routes it into the private table atomically and returns NULL in the shared row. Legacy NULL writes preserve the private year, since old directory responses contain redacted NULLs; clearing it deliberately requires the new profile RPC. Admin attempts to write another person’s year are rejected.
- Cohort connection counts, constellation, weekly progress and continent summaries are retained. A versioned, optional sharing choice is shown in the Cohort tab, with the same explanation before sign-in and in About. It explains that current and past familiarity levels contribute, who can see the results, that comparing exact totals can sometimes reveal individual levels, and that notes/stars are excluded. The previous absolute anonymity promises are removed. This is an explicit product choice to retain the feature, not a claim to have eliminated inference.
- No account is automatically opted in. Only the account can set its choice through `set_cohort_consent`; the server checks the notice version and records the timestamp. App admins cannot opt someone else in. A connection enters every shared calculation only when **both people** currently opt in. This includes the earliest date of the weekly series, node counts, group sizes and denominators. The UI labels the coverage as participating students rather than the entire cohort. A member can view aggregates without contributing their own connections.
- Unchecking the choice excludes the account's connections and history from future Cohort calculations without deleting personal records or disabling personal Stats. It cannot retract totals previously seen or copied. A new notice version requires a fresh opt-in; withdrawal remains possible from an older client. Consent records cascade when the account is erased. Pending erasure accounts are excluded immediately. Admin usage reporting and coffee matching are unchanged; this choice specifically controls the shared Cohort view.
- Admin **Delete account** invokes a server-side Edge Function. It verifies the bearer token with `Auth.getUser`, checks the caller's admin status, and validates that actor again in a service-only SQL function. The browser never receives a service-role key.
- A private retry job blocks the target account's member access and new photo uploads. Storage cleanup includes current and old profile uploads, event-photo paths, and all objects owned by the account, including abandoned uploads. It uses the Storage API, then hard-deletes Auth. User-owned foreign keys cascade, including the profile, private year, outbound/inbound relationships and history, tool backups, activity records, event/RSVP records, newsletters/checks, coffee entries/matches, formal bookings and study joins. Explicit email allowlist entries are removed too.
- Auth deletion also removes content hosted by that account (events, formal/study sessions and their dependent bookings). Other people's unrelated accounts/data are retained. Admin accounts must first have their admin role removed by another operator; the endpoint does not erase an active admin account.
- Failed requests remain pending, with **Retry deletion** available in Admin even if the profile has already disappeared. Cleanup uses batches of 100 and a bounded request budget. Large accounts may require several retries. The operation reports success only after checking that matching Storage objects and the Auth account are gone and removing the profile and retry record.

## Release protocol (one operator)

A second reviewer is optional. Passing a build or merging a PR is not release completion. Keep this PR unmerged until the backup, isolated integration suite and hosted candidate checks below pass.

1. **Backup and rehearse restore.** Export the live schema, roles, Auth and application data using the Supabase-supported backup procedure. Copy every Storage object separately: database dumps contain only file metadata. Include project configuration and record whether Vault or column encryption requires the original root key; a Developer may not be allowed to export that key. Project configuration exports are not a substitute for preserving provider secrets such as SMTP credentials. Keep dumps, credentials and photos outside Git in an access-restricted location; encrypt archives and store the encryption key separately. Record checksums, object counts, timestamps and restore results. Restore a copy into an isolated database and compare every table's row count and content digest; an untested export is not a verified backup. Keep the archive separate from the synthetic test environment and never serve real classmates’ data from a preview.
2. **Reconcile the live schema.** This project was originally managed through the SQL Editor and has no CLI migration history. Compare the live schema with the repository baseline before changing it. Do not run `db reset --linked`, blindly `db push`, or apply the complete bootstrap schema to production. Apply only reviewed upgrade SQL to the intended project. Never point the local integration fixture at a hosted project.
3. **Run isolated tests.** The `Privacy release validation` workflow boots real Supabase Auth, Postgres, Storage, Edge Functions and Mailpit with synthetic users. It starts with the rollback schema, signs into the candidate in Chromium with an eight-digit emailed OTP (matching the current production setting), completes the first-login tour, applies the upgrade, checks old-client writes, owner/peer/admin privacy, consent and withdrawal, and erases a synthetic account with more than 100 real files. `npm test` is additional coverage, not a substitute. Inspect the run and its screenshots. No production credentials are used by this workflow.
4. **Stage the exact candidate.** Test a frontend built with a dedicated test backend, including email sign-in, People and Faculty, profile saves, personal Stats and consent. Validate the actual Edge adapter with Deno and the integration run. Never accept demo mode as evidence. Keep the frontend SHA and backend migration/function revision together in the release record.
5. **Deploy backend, then check compatibility.** After verified backup, deploy `delete-student` to the exact production project, then apply the transactional privacy migration. The function validates tokens using `Auth.getUser` and requires an application admin. The SQL keeps shared years NULL and routes cached owner writes privately. Direct profile-only DELETE remains intentionally blocked, including on a rolled-back frontend. Confirm tables, RPCs, RLS and the function are ready; test the still-running old frontend before switching traffic. Do not restore shared birth years or profile-only deletion to make an old feature work.
6. **Release the frontend.** Only after backend readiness and candidate authentication tests pass, merge/promote the candidate. Main currently auto-deploys through Vercel, so merging is a production action. If Vercel access is available, a staged production deployment can be tested at its candidate URL before promotion. Do not assume a Vercel success status includes runtime tests.
7. **Post-release verification.** Sign into the actual production URL, hard-refresh it, open People and Faculty, save and reload the operator’s own profile, verify personal Stats and check consent persistence. Inspect current API/Auth errors. Destructive erasure tests use only disposable test accounts, never classmates. Record the deployed frontend SHA/URL and backend revisions, results and remaining limitations. Do not mark release complete if these checks cannot be performed.

### Compatibility and rollback

The candidate explicitly omits the legacy public birth-year column from directory reads. A missing `student_private` table does not crash the entire app; years stay unavailable. Missing profile RPCs show a temporary-unavailability error and never fall back to writing private years publicly. Permission failures and unrelated database errors are not silently hidden. This is a safety net, not permission to skip backend readiness.

Keep the preceding working frontend deployment ready to restore. Frontend rollback does not roll back the database or restore an erased account. Keep the privacy migration in place: it supports cached owner profile saves, and blocks incomplete deletion. Use a verified database restore only for an independently diagnosed database incident, with appropriate handling of any erasures since the backup. Never blindly execute a down migration that republishes birth years.

### Edge configuration

Deploy with `supabase functions deploy delete-student --project-ref YOUR_PROJECT_REF`. The committed function setting disables the gateway’s legacy JWT check; the handler itself verifies every caller through Auth and checks the app admin role. Built-in service credentials stay inside the Edge runtime and never use a `VITE_` prefix.

`DELETION_ALLOWED_ORIGINS` defaults to the three current production origins. Configure exact candidate origins separately if needed. Local origins are enabled only in the isolated integration project. No wildcard origin is used.

## Recovery and limits

Use Admin's **Unfinished account deletions → Retry deletion**. Project operators can inspect `account_deletions` privately in the dashboard to find stuck jobs, then retry the same `student_id` through the endpoint using a verified admin session. Do not manually delete Storage metadata: that leaves orphaned files. Do not delete a retry record to suppress an error or reassign a pending profile. Do not roll back the FK/policy changes while a deletion is pending. Function errors deliberately omit raw user data and upstream error details.

Deletion covers the application's **live hosted account and data**. It cannot erase copies already downloaded by classmates, browser/CDN caches, or provider backups/logs. Other users' independent copies or free-text mentions are not automatically edited. Local tool data remains on devices under the separately deferred browser-storage issue; users should clear site data on their devices. Confirm provider retention with the project owner and reapply recorded erasures before serving a restored backup. The deletion job itself is removed after success; retain any operational erasure record only under the project's agreed private retention policy.

The local tests run PostgreSQL via PGlite with modeled Supabase Auth/Storage tables, grants and roles, plus an injected Edge handler. They validate schema/RLS/cascades and request sequencing/failure behavior. Those unit tests do not emulate GoTrue's own internal tables, Storage's object backend/CDN, or deployed Edge infrastructure; the real Supabase integration and hosted checks above are required for release.
